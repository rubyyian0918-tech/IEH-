# 階段 0 技術驗證｜初步結論（文件研究版）

> 日期：2026-09-30　狀態：**文件研究完成，實測尚未開始**
> 這份是依官方文件與官方 SDK 原始碼整理的初步判斷。每一項都要等你完成準備工作、用驗證程式實測後才算定案。

## 一句話結論

MVP 要做的事，Meta API **大多做得到**。最大的風險不在功能，而在**審查與開發模式的限制**：
在通過 App 審查之前，webhook 可能只會通知 App 角色成員的留言，Instagram 的即時通知更是一定要審查通過才會送。
所以影子模式的前期要準備用「定時補抓」撐住，不能只靠 webhook。

## 能做／不能做／有條件（摘要）

| 平台 | 動作 | 結論 | 條件 |
|---|---|---|---|
| FB 粉專 | 讀取貼文、主留言、回覆 | 可做 | 留言者資訊只有用粉專 token 查才會回；上線需 `pages_read_user_content` 審查 |
| FB 粉專 | 回覆、隱藏、取消隱藏、刪除 | 可做 | `pages_manage_engagement`（回覆模式才需要） |
| FB 粉專 | 按讚留言 | 可做 | 同上（MVP 不做） |
| FB 粉專 | 封鎖使用者 | 有條件 | 有 API，但能否直接用留言者 ID 封鎖未確認（MVP 不做） |
| FB 粉專 | webhook 即時收留言 | 有條件 | 每個粉專都要訂閱；**開發模式可能只收到 App 角色成員的留言** |
| FB 粉專 | 偵測品牌原生回覆 | 有條件 | webhook 的 `from.id`＝粉專 ID 即為品牌回覆；管理員若用個人身分回覆則不會被認出，需實測 |
| FB 廣告 | 讀取／處理廣告留言 | 可做 | 從廣告的 `effective_object_story_id` 讀留言，用粉專 token |

| FB 廣告 | 廣告留言進 webhook | 待實測 | 官方沒寫清楚，業界有漏送回報 → 一定要搭配定時補抓 |
| IG | 讀取貼文與 Reels 留言、回覆 | 可做 | 讀取也需要 `instagram_manage_comments`（所以影子模式就要送審這個權限） |
| IG | 回覆、隱藏、取消隱藏 | 可做 | 回覆只能回主留言 |
| IG | 刪除他人留言 | 待實測 | 各來源說法不一 |
| IG | 按讚留言 | 有條件 | **2026-04 起可做**，需要新權限 `instagram_manage_engagement` 並送審（與原本文件的認知不同） |
| IG | 封鎖用戶 | 不可做 | 沒有 API |
| IG | webhook 即時收留言 | 有條件 | 需 App 上線（Live）＋`instagram_manage_comments` 進階權限＋公開帳號；**開發模式基本收不到一般使用者留言** |
| IG | 廣告留言 | 可做 | webhook 會直接帶 `ad_id`，不必自己對應；也能從廣告查出媒體再讀留言 |

| 共通 | 去重 | 可做 | webhook 至少送一次、可能重複與亂序；本機自我測試已通過 |
| 共通 | 資料刪除、取消授權回呼 | 可做 | 上線前必須設定；驗證程式已實作 |

## 對 MVP 範圍的建議

1. **收留言改成「補抓為主、webhook 為輔」起步**，而不是反過來。
   審查通過前，定時補抓（例如每 2–5 分鐘）是唯一可靠的來源；審查通過後再把 webhook 變成主要來源、補抓降為保險。
   這不增加範圍（原本就要做補抓），只是調整先後順序。
2. **送審分兩次**：
   - 第一次（影子模式）：`pages_show_list`、`pages_read_engagement`、`pages_read_user_content`、`pages_manage_metadata`、`instagram_basic`、`instagram_manage_comments`、`ads_read`（視需要加 `business_management`）。
   - 第二次（回覆模式）：`pages_manage_engagement`（按讚需要時再加 `instagram_manage_engagement`）。
   - 注意：IG 的回覆／隱藏也包在 `instagram_manage_comments` 裡，第一次送審的示範影片可能就要示範 IG 回覆，審查員才會通過。這點要在送審前再確認。
3. **公司登記要提早**：審查需要商家驗證，影子模式要接真實客戶就得先通過審查，所以公司登記會直接卡住階段 1。
4. **資料表要預留**：
   - `contents` 與廣告是多對多（一篇貼文可被多則廣告使用）→ 建議新增 `content_ads` 關聯表，而不是只在 `contents` 放一個廣告 ID。
   - `comments` 要能記錄「編輯、刪除、隱藏」事件（FB 會送，IG 不會送、要靠補抓比對）。
5. **API 版本鎖定 v26.0**，每個版本大約兩年後淘汰，要排定升級。

## 實測才能回答、而且會影響決策的問題

依影響大小排序：

1. 開發模式下，把設計夥伴的粉專管理員加成測試人員後，**一般網友的留言**會不會進 webhook？補抓時看不看得到留言者？→ 決定影子模式能不能在送審前開跑。
2. FB 廣告（含動態素材）的留言會不會穩定進 webhook？
3. 管理員在 FB App 以「個人身分」而非「粉專身分」回覆時，系統能否辨識？
4. IG 能否刪除他人留言？IG 廣告留言的回覆／隱藏是否要帶 `ad_id`？
5. 小粉專的呼叫額度（依互動人數計算）在廣告爆量時夠不夠用？

驗證程式對應的指令見 [`../README.md`](../README.md)。

## 需要產品負責人決定的事

- 是否接受「審查通過前，影子模式只能接 App 角色成員管理的粉專，並以補抓為主」這個前提。
- IG 按讚現在做得到：要不要列入回覆模式（會多送審一個權限）。
